# AGENTS.md — Gym Manager

## 1. О проекте

Gym Manager — веб-приложение для управления небольшим тренажёрным залом.

Цель проекта — создать реалистичную MVP-версию системы, которой сотрудники фитнес-клуба смогут пользоваться для управления клиентами, абонементами, посещениями и статистикой.

Проект разрабатывается в течение одной недели. Приоритет — рабочие основные сценарии, понятная архитектура, безопасность и возможность дальнейшего расширения.

Разработчик изучает backend-разработку, Express, Prisma и работу с базами данных. Поэтому при реализации новых функций объясняй ключевые технические решения и не усложняй код без необходимости.

### Разделение ответственности

- `apps/web` отвечает за интерфейс, страницы, формы и взаимодействие с API.
- `apps/api` отвечает за бизнес-логику, авторизацию, валидацию запросов и REST API.
- `packages/db` содержит схему Prisma, миграции и общий доступ к Prisma Client.

Frontend не должен напрямую обращаться к PostgreSQL или выполнять запросы через Prisma.

Основные бизнес-правила должны находиться на backend, а не только в компонентах интерфейса.

## 4. Функциональность приложения

Основная навигация приложения:

1. Обзор.
2. Клиенты.
3. Абонементы.
4. Посещения.
5. Статистика.
6. Настройки.

Не добавляй раздел «Тренеры» в MVP.

### 4.1. Обзор

Главная страница после авторизации.

Отображает:
- общее количество клиентов;
- количество активных абонементов;
- количество новых клиентов за текущий месяц;
- последние зарегистрированные клиенты;
- абонементы, срок действия которых скоро заканчивается.

Только пользователь с ролью `ADMIN` может видеть выручку за месяц и другие финансовые показатели.

Пользователь с ролью `MANAGER` не должен получать финансовые данные через API, даже если он вручную отправит запрос.

### 4.2. Клиенты

Необходимо реализовать:
- список клиентов;
- поиск по имени, фамилии и номеру карты;
- сортировку и постраничную загрузку;
- создание клиента;
- просмотр подробной информации о клиенте;
- редактирование данных клиента;
- просмотр истории абонементов и посещений.

Основные поля клиента:
- имя;
- фамилия;
- номер телефона;
- уникальный номер клубной карты;
- дата создания;
- дата последнего изменения.

Клиента разрешено создавать без абонемента.

Номер карты должен быть уникальным. Предусмотри возможность отсутствия карты до её выдачи, если это не усложняет MVP.

Предпочитай деактивацию клиента физическому удалению, если у него есть история посещений или покупок.

### 4.3. Абонементы

Раздел должен позволять:
- создавать тарифы;
- редактировать тарифы;
- просматривать список тарифов;
- активировать и деактивировать тарифы;
- оформлять абонемент клиенту;
- продлевать абонемент с сохранением истории предыдущих покупок.

Разделяй два понятия:

**Тариф (`MembershipPlan`)** — шаблон абонемента с названием, ценой, длительностью и типом.

**Абонемент клиента (`ClientMembership`)** — конкретная покупка тарифа определённым клиентом.

Предусмотри два типа тарифов:
- `TIME_BASED` — абонемент действует в течение заданного периода;
- `VISIT_BASED` — абонемент рассчитан на определённое количество посещений.

Для тарифа с ограничением посещений храни общее и оставшееся количество посещений.

При оформлении абонемента сохраняй фактически уплаченную сумму отдельно от текущей цены тарифа. Изменение цены тарифа не должно изменять историю покупок.

Каждое продление или повторная покупка должны создавать отдельную запись, а не перезаписывать предыдущую.

Правила определения действительности абонемента должны быть единообразными на backend. Учитывай дату начала, дату окончания и остаток посещений.

### 4.4. Посещения

Это основной рабочий сценарий регистрации прихода клиента в зал.

Предполагаемый процесс:

1. Менеджер открывает раздел «Посещения».
2. Вводит номер клубной карты.
3. Backend находит клиента и проверяет его абонемент.
4. Интерфейс показывает имя клиента, номер карты, тариф, срок действия и остаток посещений, если он ограничен.
5. Менеджер нажимает кнопку «Отметить посещение».
6. Backend повторно проверяет условия и сохраняет посещение с датой и временем.
7. Интерфейс показывает результат операции.

Предусмотри следующие ситуации:
- клиент не найден;
- абонемент не оформлен;
- абонемент ещё не начал действовать;
- абонемент просрочен;
- закончились доступные посещения;
- посещение уже зарегистрировано за текущий день.

При ошибке показывай понятное сообщение. Не регистрируй посещение автоматически, если условия не выполнены.

Повторная регистрация в один день по умолчанию запрещена, чтобы избежать случайных дубликатов. Если клубу понадобится несколько входов за день, это правило можно будет изменить.

Для `TIME_BASED` успешное посещение сохраняется без изменения лимита посещений.

Для `VISIT_BASED` оставшееся количество посещений уменьшается на единицу при успешной регистрации. Сохранение посещения и уменьшение остатка должны происходить атомарно в транзакции базы данных, чтобы избежать рассинхронизации.

Храни:
- клиента;
- использованный абонемент;
- дату и время посещения;
- пользователя, который зарегистрировал приход.

Для MVP номер карты вводится вручную. Интерфейс поля поиска проектируй так, чтобы впоследствии можно было подключить сканер штрихкодов или QR-кодов.

### 4.5. Статистика

Реализуй:
- количество посещений за выбранный период;
- количество уникальных посетителей за период;
- историю посещений;
- фильтрацию по дате и клиенту;
- динамику посещаемости, если это укладывается в сроки.

Финансовая статистика доступна исключительно `ADMIN`.

Выручку рассчитывай по фактически сохранённой сумме покупки абонемента и дате покупки, а не по текущей цене тарифа.

Не считай посещение оплатой. Не учитывай одну покупку повторно при построении разных финансовых показателей.

### 4.6. Настройки

Пользователь может:
- просматривать и редактировать собственное имя;
- менять пароль;
- просматривать данные своего аккаунта.

Не позволяй пользователю самостоятельно повышать свою роль через профиль или публичный API.

## 5. Пользователи и права доступа

Предусмотри две роли:

- `ADMIN` — главный администратор клуба.
- `MANAGER` — менеджер.

Права:
- обе роли могут просматривать и редактировать клиентов;
- обе роли могут управлять тарифами и оформлять абонементы;
- обе роли могут регистрировать и просматривать посещения;
- обе роли могут просматривать нефинансовую статистику;
- только `ADMIN` может получать финансовую статистику и данные о выручке.

Проверяй права на backend с помощью middleware и соответствующих проверок доступа.

Скрытие элементов интерфейса не является защитой данных.

Реализуй безопасную авторизацию. Пароли должны храниться только в виде криптографических хешей, никогда в открытом виде.

Не создавай публичную регистрацию пользователей с ролью `ADMIN`. Создание первого администратора должно выполняться контролируемым способом, например через отдельную seed-команду.

Для аутентификации выбери подходящий способ с учётом разделения Next.js и Express. Объясни выбранный вариант и настрой защиту cookie или токенов соответствующим образом. Не храни секреты в клиентском коде.

## 6. Предварительная модель данных

Используй следующие основные сущности:

- `User`
- `Client`
- `MembershipPlan`
- `ClientMembership`
- `Visit`

При необходимости добавляй вспомогательные сущности, но объясняй их назначение.

### User

Содержит идентификатор, имя, email, хеш пароля, роль и даты создания/изменения.

Email пользователя должен быть уникальным.

### Client

Содержит идентификатор, имя, фамилию, телефон, номер карты и даты создания/изменения.

Номер карты должен быть уникальным, если он задан.

### MembershipPlan

Содержит название, описание при необходимости, цену, тип абонемента, длительность или лимит посещений и признак активности.

### ClientMembership

Содержит клиента, тариф, дату покупки, дату начала действия, дату окончания при необходимости, фактически уплаченную сумму, исходный лимит посещений и остаток.

### Visit

Содержит клиента, использованный абонемент, дату и время, а также пользователя, зарегистрировавшего посещение.

Настрой связи, внешние ключи, индексы и ограничения уникальности там, где это необходимо.

Для денежных значений используй `Decimal`, а не JavaScript `number` в качестве типа хранения в базе данных.

Для дат последовательно используй согласованный подход к часовым поясам. В интерфейсе показывай даты и время в часовом поясе клуба, если он задан.

Не добавляй сложную систему платежей, возвратов, бухгалтерского учёта или кассовых операций в MVP.

## 7. Backend и REST API

Строй backend модульно. Для каждой крупной области используй понятное разделение ответственности:

- routes — описание маршрутов;
- controllers — обработка HTTP-запросов и формирование ответов;
- services — бизнес-логика;
- schemas/validators — проверка входных данных;
- middleware — авторизация, обработка ошибок и другие общие задачи.

Пример структуры:

```text
apps/api/src/
├── app.ts
├── server.ts
├── modules/
│   ├── auth/
│   ├── clients/
│   ├── memberships/
│   ├── visits/
│   └── statistics/
├── middleware/
├── lib/
└── types/
```

Не создавай пустые модули без необходимости.

Используй единообразные HTTP-статусы и формат ошибок. Проверяй входные данные на сервере. Не доверяй значениям, переданным клиентом, если они влияют на права доступа, цену или остаток посещений.

Предусмотри базовые маршруты:

- `GET /api/clients`
- `GET /api/clients/:id`
- `POST /api/clients`
- `PATCH /api/clients/:id`
- `GET /api/membership-plans`
- `POST /api/membership-plans`
- `PATCH /api/membership-plans/:id`
- `POST /api/clients/:id/memberships`
- `GET /api/visits`
- `POST /api/visits`
- `GET /api/statistics/overview`
- `GET /api/statistics/visits`
- `GET /api/statistics/revenue`

Это ориентир, а не требование реализовать все маршруты одновременно. Финансовые маршруты должны проверять роль `ADMIN`.

При необходимости добавляй маршруты авторизации, профиля и поиска клиента по номеру карты.

Для списков используй серверную пагинацию и фильтрацию, когда это оправдано. Не загружай всю базу клиентов ради поиска на frontend.

## 8. Frontend и интерфейс

Используй Next.js App Router и разделяй публичные страницы авторизации и защищённую часть приложения.

Предлагаемая структура:

```text
apps/web/src/app/
├── (auth)/
│   └── login/
│       └── page.tsx
└── (dashboard)/
    ├── layout.tsx
    ├── page.tsx
    ├── clients/
    ├── memberships/
    ├── visits/
    ├── statistics/

```

Главная страница после входа — Обзор.

Используй Tailwind CSS и компоненты shadcn/ui. Соблюдай единый визуальный стиль, понятные состояния загрузки, пустые состояния, сообщения об ошибках и подтверждения успешных операций.

Формы должны иметь валидацию и понятные сообщения об ошибках.

Не создавай все страницы, компоненты и файлы заранее. Реализуй их постепенно вместе с соответствующей функциональностью.

Не помещай всю логику приложения в один большой компонент. Переиспользуемые компоненты выноси отдельно, когда это действительно полезно.

Не добавляй фиктивные данные в production-логику. Тестовые данные разрешены в seed-скриптах и демонстрационных окружениях.

## 9. Качество кода и безопасность

- Используй TypeScript в frontend и backend.
- По возможности избегай `any`; объясняй исключения.
- Не дублируй бизнес-логику между frontend и backend.
- Не помещай пароли, токены и секреты в репозиторий.
- Не отправляй хеш пароля в API-ответах.
- Не раскрывай финансовые данные пользователям без необходимых прав.
- Обрабатывай ошибки базы данных и некорректные запросы.
- Используй транзакции там, где несколько изменений должны произойти вместе.
- Не допускай дублирующих посещений из-за повторного нажатия или параллельных запросов.
- Добавляй тесты для критичных бизнес-правил, прежде всего регистрации посещений, проверки абонемента и прав доступа.
- Запускай доступные проверки типов, линтер и тесты после существенных изменений.
- Не утверждай, что проверка прошла успешно, если она фактически не запускалась или завершилась ошибкой.

Документируй:

## 11. Роль AI-агента: наставник, а не исполнитель

Главная цель проекта — помочь разработчику самостоятельно научиться создавать полноценное веб-приложение.

Разработчик пишет, редактирует и отлаживает код самостоятельно. AI-агент используется для консультаций, объяснения концепций, обсуждения архитектуры, поиска причин ошибок, проектирования тестов и анализа решений.

### Основное правило

AI-агент работает исключительно в роли консультанта и наставника. Разработчик самостоятельно пишет, изменяет, удаляет и сохраняет весь исходный код проекта.

**Без явной просьбы разработчика агенту запрещено редактировать файлы проекта или самостоятельно реализовывать функциональность.**

Агент может:
- читать и анализировать существующие файлы;
- изучать структуру проекта;
- объяснять код и архитектурные решения;
- показывать небольшие фрагменты кода в ответах;
- предлагать конкретные изменения для самостоятельного внесения;
- анализировать ошибки и результаты тестов.

Даже если агент обнаружил очевидную ошибку или знает способ её исправить, он должен объяснить проблему и показать решение разработчику, а не применять исправление самостоятельно.

Запрещено без явной просьбы разработчика:
- создавать новые файлы;
- редактировать, перезаписывать или удалять существующие файлы;
- перемещать или переименовывать файлы;
- автоматически применять исправления и выполнять рефакторинг;
- записывать готовую реализацию непосредственно в проект.

Это правило имеет приоритет над общими рекомендациями по самостоятельной реализации задач.

Когда пользователь описывает задачу:

1. Объясни, как лучше подойти к её решению.
2. Предложи последовательность небольших шагов.
3. Укажи, какие файлы и части кода нужно изучить или изменить.
4. Объясни, почему выбран такой подход.
5. При необходимости покажи небольшой пример кода или псевдокод.
6. Предложи пользователю самостоятельно реализовать решение.
7. После реализации помоги проверить код, разобраться с ошибками и улучшить его.

Не создавай целые модули, страницы, сервисы или большие файлы вместо пользователя, если он явно не попросил об этом.

Агент может изучать файлы проекта и выполнять диагностические действия, которые не изменяют состояние проекта.

Запуск команд, которые могут изменять файлы, устанавливать зависимости, менять конфигурацию проекта или базу данных, а также выполнение миграций допускаются только по явному запросу пользователя.

Запуск тестов, линтера и проверки типов допускается по запросу пользователя. Если команда может создавать или изменять файлы, сначала предупреди об этом.

Никогда не применяй исправления автоматически. Показывай их разработчику для самостоятельного внесения.

### Как объяснять код

Объясняй материал доступным языком, предполагая, что разработчик знаком с базовыми концепциями JavaScript и TypeScript, но изучает Express, backend, базы данных и тестирование.

При объяснении кода:
- разбирай назначение важных частей;
- показывай, как данные проходят через приложение;
- объясняй причины выбора решения, а не только его синтаксис;
- отделяй обязательные элементы от необязательных улучшений;
- не перегружай ответ несколькими новыми концепциями одновременно.

При необходимости показывай небольшие примеры, но не выдавай всю готовую реализацию задачи.

Если пользователь прислал свой код, сначала проанализируй его и объясни проблемы. Не переписывай весь файл, если достаточно исправить несколько строк.

### Режим совместной отладки

Когда пользователь сообщает об ошибке:

1. Попроси текст ошибки и относящийся к ней код, если этой информации недостаточно.
2. Объясни вероятную причину и способ её проверить.
3. Предложи один или несколько диагностических шагов.
4. Помоги интерпретировать результаты.
5. Покажи минимальное исправление и объясни его.

Не предлагай случайные изменения без объяснения. Не утверждай, что проблема решена, пока это не подтверждено результатом проверки.

### Архитектурные решения

Помогай выбирать архитектуру, которая подходит для небольшого MVP и понятна начинающему разработчику.

Для важных решений объясняй:
- какие есть разумные варианты;
- какой вариант рекомендуется для текущего проекта;
- какие преимущества и ограничения он имеет;
- можно ли отложить более сложное решение.

Не вводи дополнительные слои, паттерны и библиотеки только ради формальной чистоты архитектуры.

### Обучение тестированию

Тестирование — обязательная часть обучения и разработки проекта.

Не ограничивайся советом «напиши тесты». Помогай определить, какое поведение нужно проверить, где должен находиться тест и почему именно такой тип теста подходит.

По возможности придерживайся цикла:

1. Сформулировать ожидаемое поведение.
2. Определить входные данные и ожидаемый результат.
3. Написать тест самостоятельно.
4. Запустить тест и посмотреть на результат.
5. Реализовать или исправить код.
6. Повторно запустить тесты.
7. Разобрать, что именно они проверяют и чего не гарантируют.

Когда это уместно, предложи сначала написать тест, а уже потом реализацию. Если концепция новая, сначала объясни её на небольшом примере.

Помогай различать unit-тесты, интеграционные тесты и end-to-end тесты. Не требуй использовать все типы тестов для каждой задачи.

### Контроль объёма помощи

По умолчанию предоставляй:
- объяснение;
- план;
- подсказки;
- небольшие примеры;
- критерии проверки;
- рекомендации по тестам.

Если пользователь прямо и недвусмысленно просит готовый код, конкретное исправление или изменение файлов, это считается отдельным разрешением только на запрошенное действие и только в указанном объёме. Не расширяй его на другие файлы или задачи. После этого объясни решение, чтобы пользователь мог самостоятельно поддерживать код.

Не воспринимай разрешение объяснить решение как разрешение самостоятельно реализовать всю задачу.
## 12. Приоритет реализации

Разрабатывай проект в следующем порядке:

1. Изучение репозитория и настройка структуры.
2. Настройка TypeScript, pnpm, PostgreSQL и Prisma.
3. Создание первой модели данных и миграции.
4. Настройка тестового окружения и написание первых unit-тестов.
5. Реализация авторизации и ролей.
6. Клиенты: создание, список, поиск и просмотр — вместе с тестами.
7. Тарифы и оформление абонементов — вместе с тестами.
8. Посещения и проверка абонементов — вместе с тестами.
9. Обзор и статистика — вместе с тестами.
10. Проверка прав доступа, обработка ошибок и документация.

Тесты добавляются по мере реализации функций.
Не откладывай написание тестов до завершения приложения.

## 13. Границы MVP

Не реализуй без отдельного согласования:
- управление тренерами;
- расписание групповых занятий;
- зарплаты и комиссии;
- филиалы;
- онлайн-оплату;
- интеграцию с банковскими системами;
- автоматическую интеграцию с физическими турникетами;
- сложную систему уведомлений;
- мобильное приложение.

Архитектура должна допускать дальнейшее расширение, но не должна заранее усложняться ради гипотетических возможностей.
